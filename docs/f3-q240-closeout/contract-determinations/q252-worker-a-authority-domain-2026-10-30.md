## 3. Decisions A-F

**A. Can world Y be built through a valid supported interface?** Yes as a WORLD (a "new decision under Y" is exactly what the contract prescribes: `02` section 4 rule 5 "There is no re-bind. A changed configuration needs a new decision"; `docs/effective-configuration-binding.md` section 7), but NOT as "decision under X, live rebuilt under Y, all else equal". The only interface that changes the live ECB domain is the host manifest at workflow construction. A Registry edit does not (Registry verifies, never supplies, the domain). A different family/class declaration does not (`GovernedScope` has no domain; family rows contain no domain: `effective_configuration_binding.py:47,154`). A resolver-side change does not move the ECB leaf at all (it is read from `_gl_authority`) and is refused by `authority_domain_mismatch`. `host_policy_binding` (pin-export/claim argument) carries a scope domain, but that is a different member (pin payload `authority_domain`), is bound by `binding_digest` to the profile (`authorization_pin_export.py:144`) and does not feed the ECB. Post-construction mutation of the manifest is impossible through the object (deep copy `bounded.py:1291`) and, if the private `_gl_authority` or the module-level `_declared_authority` were altered, the first consistent-lifecycle check is `manifest_authority_changed` (`registry_governed_lifecycle.py:307-309`) at decide/execute only; pin-export and claim do not run it (see PATCH route in section 5).

**B. First mandatory guard to refuse (execute, in code order, for a Y world fed with the X proposal `P_X`):** `_gl_reverify` passes if `W_Y` is internally consistent (Registry material for Y supplied). In the base resolve: `manifest_digest_mismatch` (`bounded.py:2619`) is the first guard in code order (it is computed at `2266`, before the authority-context read), plus whichever of `authority_domain_mismatch` / `approval_operation_binding_mismatch` apply to the rest of the fixture; D-1 observed `[approval_operation_binding_mismatch, manifest_digest_mismatch]` (consistent d2 world + P1) and `[authority_domain_mismatch, manifest_digest_mismatch]` (original A25(a) route). The ECB is not consulted in either (`registry_governed_lifecycle.py:267-268`). For pin-export: the host-binding/catalogue guard at `authorization_pin_export.py:142-149` (raised, pre-resolve) when the Y world carries a Y host body/profile; otherwise `unknown` from `current != current_binding` at `:181`.

**C. Is the ECB comparison legitimately reachable?** Yes, exactly when every record is re-authored under Y and the proposal is rebuilt (`P_Y`) against the old decision `D_X` (D-1 Q2-A2(ii)); it then refuses `[authorization_binding_changed]` but the base binding differs in `{manifest_digest, proposal_commitment}` too, so the refusal would occur with the ECB leaf deleted. Held invariant required to reach the ECB at all: `reasons == []`. Invariants that cannot be held while the domain moves: `manifest_digest` (function of the manifest), `proposal_commitment` (function of `manifest_digest`), approval operation binding, and on the pin fixture `binding_digest`/`catalogue_digest`/`approval_commitment`.

**D. Is an isolated domain change consistent with the authority invariants?** No. The domain is the identity of the issuing authority scope: every authority record is validated against the context's `(institution_id, authority_domain)`; evidence statements and purpose status bind it; Registry issuer authority and selection scope bind it; the manifest declares it as part of the operation contract and the proposal commits to the manifest. A state where the Control Plane's governed scope says Y while the manifest digest, proposal, approvals and records still say X is not a state the supported model can produce; it is exactly the state the base guards exist to refuse. The correct legitimate outcome for a domain change is "refuse the old decision; mint a new decision" (rule 5), and that is what happens, redundantly. (INFERENCE from the cited guards; the ECB leaf is a defense-in-depth echo of `manifest_digest`.)

**E. Which legs are inherently unreachable/inapplicable?** None by contract text for THIS member.
* Execute: applicable (`06` section 3 A; refusal + durable `EffectTimeRefusal`).

## 8. Top findings and uncertainties

1. The ECB domain leaf is a function of the manifest that is already committed by `manifest_digest`; a supported change of it always moves `manifest_digest` and `proposal_commitment` and is refused by an earlier or concurrent base guard. "All else equal" is not a state the supported model can express.
2. Execute is JOINT-ONLY (D-1 Q2-A2(ii) reaches the ECB with base diff `{manifest_digest, proposal_commitment}`); pin-export is GUARD-FIRST at `authorization_pin_export.py:144-147` for any consistent Y world; claim is JOINT-ONLY. No leg is UNREACHABLE-BY-CONTRACT; the "F4-only" pin-export limit does not exclude this member (F4 is the one pin-capable workflow and bears the domain).
3. D-1's graft is sound as a sensitivity probe but only for execute and only via an unsigned store write; the live pin-export and claim legs have no evidence for this member. The hub's own note that the pin-export graft "was isolable and was not run" is plausible but its donor must share the recipient's profile (fixture plumbing UNVERIFIED).
4. New: a seam-patch isolation (patch `_declared_authority`, supply Y-signed Registry material) equalizes the base binding without any store write and mirrors the A25(b)(c)(d) PATCH practice already scored PASS; it is also the cheapest route on pin-export/claim (those legs skip `_gl_reverify`). Not run; not a supported interface; evidential class equals the graft's.
5. The refusal code `authorization_binding_changed` cannot attribute a refusal to a member; any future case must use the complementary base/ECB diff as D-1 did, and must include a comparison-side or stamping-side mutant in addition to M06 (which only changes derivation and is outcome-equivalent on natural routes).

Uncertainties: no execution; same-lineage; the readjudication/D-2 raw rows were not opened; pin-fixture generalization; Architect's interpretation of "valid supported pathway"; `bounded.py` `_resolve_inputs` range `~2257-2605` and a few `runtime_authority.py` evidence/purpose lines are approximate (marked `~`).

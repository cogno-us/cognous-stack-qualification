## 3. Answers to the five questions

**(1) Must each member be exercised through a supported natural path, or is "perturbing the member changes the digest and causes refusal" enough?**
The frozen text requires only the second: each member perturbed independently changes the digest and execute/pin-export refuse with the code (`03` L23); `02` rule 2 defines refusal on "unequal to the live value". Neither document requires natural reachability, live-side routing, or non-joint attribution. Evidence already in the record that matches the literal E1 form: original A19 execute 22/22 persisted-side reseal rows PASS (each member alone perturbed, digest resealed, refusal with durable `EffectTimeRefusal`; `verdict.md` section 2), A02 nine live perturbations, A25 b/c/d/d' live-side (patched / signed) PASS, A14 scope replay PASS, D-1 component layer (digest changes exactly with the member leaf) and D-1 graft/host cases. What the persisted-side rows cannot show is live-side derivation sensitivity (M06 survived: a constant live domain behaves identically). The contract text does not say that live-side sensitivity per member must be shown; record 12's risk statement does ("not independently shown to cause refusal could be silently dropped").

**(2) Is joint refusal with another guard first acceptable under the contract?**
Two distinct cases. (a) *Another guard first* (D-1 Q2-A2 (i),(iii); Q3-E1): the decision is refused, but by a different code; the ECB is not consulted (`lifecycle.py:267` per D-1). `02` section 4 intro makes this safe ("none removes a refusal another check produced") and rule 3 says the member grants nothing, so there is no safety hole. But it does not produce `authorization_binding_changed`, so it cannot count as the E1 clause "refuse with `authorization_binding_changed`" for that member. (b) *Joint* (Q2-A2 (ii), Q3-E2): the binding code is produced, but the diff contains other leaves, so the refusal is not attributable to the member. The contract is silent on whether either may substitute for isolation. So: acceptable as safe behaviour, not shown to satisfy any text that demands per-member attribution, and no record says it is accepted as a substitute.

**(3) Did the Architect or any contract record accept the isolation limits as a documented coverage limit?**
No. Searched 02, 03, 06, 07, 08, 09, 10, 11, 12, 13, 14, r08-v8-contract, hub verdict/README, #240. Closest items: (i) the original qualifier's "Coverage limits (not passes)", which is a qualifier statement; (ii) record 12's fallback status "not independently demonstrated for this member", which defines how a non-isolable outcome is *labelled*, not that it is accepted; (iii) record 13 decision 3 and the #240 "Genuine Architect decisions (2)", both of which state the question is still the Architect's. The masked-host *limit* is documented (CP doc at `8616d5f`, section on "Host change masked by a stricter Registry value"; the `739efe7` doc section 10 lacks it, which the original verdict flagged as a documentation gap), but its scope is F4 scalars / ObservationPolicy values, and D-1 showed the host_profile_digest member does refuse a masked class-age host edit on the F5 workflow. A documented limit is not the same as an Architect-accepted coverage limit.

**(4) What exact criterion would remain unmet if natural/independent end-to-end isolation IS mandatory?**
Using record 12's own criterion text (the only precise statement) plus its pin-export requirement:
- *Q2 (authority_domain):* one case in which a decision is minted under domain X, the live side is rebuilt under domain Y, base-binding diff empty and ECB diff exactly {digest, members.scope.authority_domain}, through supported interfaces with no guard disabled and no store write, producing `authorization_binding_changed` + durable `EffectTimeRefusal` on execute and the 06-section-3.B non-active / payload-None outcome on pin-export; produced by a designated independent owner. D-1 (`verdict.md`): "MET ONLY BY GRAFT", "Natural isolation is structurally impossible on the live side without disabling a guard"; the graft needs the documented unsigned-store writer capability; pin-export leg not exercised ("pin-export and claim paths ... not covered"); no independent-owner designation exists (REVIEW-ADDENDUM item 0). So if "naturally reachable" is mandatory, the criterion is *unsatisfiable by construction* (manifest_digest and resolver-domain checks at `bounded.py:2619`, `:2298` move with the domain), which would make it a contract/oracle defect for the Architect to rule on, not an implementation shortfall I can identify.
- *Q3 host_profile_digest:* D-1 Q3-H1 meets the execute leg on one workflow (F5 class-age, masked-host route), under self-written criteria (REVIEW-ADDENDUM item 3). Unmet: pin-export leg; other governed workflows (policy composition, class-unreadable); independent owner; unmasked-edit negative control (listed as not examined).
- *Q3 effective_profile_digest:* an isolated case with ECB diff exactly {digest, members.effective_profile_digest}. D-1: guard-first (approval) or joint (diff also includes `families.0.effective_policy_digest`, per REVIEW-ADDENDUM item 2). The member equals `catalogue_digest` by freeze design (`02` section 4: "equals `catalogue_digest` for profile-bearing workflows"), so a natural isolating route may not exist; a graft with a suitable donor was not run. Unmet today: any isolated end-to-end case, and the independent-owner and pin-export legs.

## 4. Conclusions

**Q2: AMBIGUOUS (do not close, do not call failed).**
Precisely: (i) Contract text (02, 03, 06) does not require *natural reachability*, and where the oracle itself names the scope member (E8) it prescribes a replay/graft negative control; on text alone natural isolation is NOT MANDATORY. (ii) Record 12 puts A25(a) in Class A ("required for the current F3-A acceptance boundary") and asks for "one independent isolation ... execute and pin-export"; D-1 supplies a graft-only, execute-only, non-independent result. (iii) Whether graft-only evidence, or "not independently demonstrated for this member", satisfies the Class A requirement is expressly reserved to the Architect (record 13 decision 3; #240 Genuine Architect decision 2). Nothing resolves (ii) against (iii). I will not invent the expectation. Recommended status wording: "A25(a): mechanism evidence by graft (execute only); naturally reachable isolation structurally unavailable; Architect disposition pending."

**Q3: AMBIGUOUS, split by member.**
- host_profile_digest: contract text does not require more than the persisted-side and D-1 evidence for the execute leg; Class A residual is pin-export, other workflows, independence. The natural-route question is moot (a natural route was found on one workflow).
- effective_profile_digest: contract text does not require independent isolation (E1 says perturbation changes the digest and refuses; satisfied by persisted-side reseal and joint/guard-first refusal). Record 12 item 2 says "Two independent fixtures needed" (host and effective) and the effective one has no natural isolating route. Same Architect-reserved question as Q2.

**Strongest counter-argument to AMBIGUOUS**
- *For MANDATORY:* record 12 says in plain words that Class A is "required for the current F3-A acceptance boundary" and that the items "stay inside" it, and both the closeout (14 section 6) and #240 say "none waived"; the stated reason is concrete (a regression silently dropping a member would go undetected by persisted-side tests, and M06 did survive). Reading record 13 decision 3 as genuinely open underweights record 12.
 Rebuttal: record 12 itself supplies the "if not isolable" status, record 13 and #240 independently call the question open, and the Class A definition is the lead builder's, reported not quoted from the Architect.
- *For NOT MANDATORY:* the frozen text never asks for isolation or natural reach; the original qualifier scored it as a coverage limit with an optional recommendation and still returned a verdict; a criterion that D-1 shows is structurally unsatisfiable on the live side cannot be an acceptance gate without an explicit Architect ruling; E8 itself prescribes replay for scope.
 Rebuttal: the lead builder's later records (12-14) and the Architect directive as reported moved the items into the acceptance boundary after the fact, and nothing in the repo shows the Architect adopting the original qualifier's "coverage limit" reading.

# Q6-A contract analysis: test_negative_incorrect_journal_linkage_is_detected[journal]
CP 739efe7; Verifier 39d46b4; read-only. Subordinate of lead builder session (not independent).

CONCLUSION: CONTRACT DOES NOT REQUIRE LINKAGE on plain journal (skip NOT APPLICABLE as a contract matter; still an unexecuted-by-design, never-exercised stage-lie half).

A. Linkage is an operation-identity profile feature, not a journal-mode requirement.
 - CP bounded.py: decide() 1634-1639 / execute() 1684-1695 / local_authority_effect.py 441-454 all pass check_ref only `if (self._identity or self._freshness)`; _record_check 1327-1336 passes check_id only `if check_id`; record_resolution_check 627-661 uses `check_id or str(uuid.uuid4())` (line 654) -> on plain journal the ResolutionCheck gets a fresh uuid unrelated to journal id (_resolve 2058 creates the journal id separately). So the test comment "same as decision/effect paths" is accurate: same gating at all three sites.
 - docs/opt-in-profiles.md:11 (operation-identity/0.1): "the journal `check_id` carried by check events, resolution checks and the join row". Line 3: "Nothing on this page is default behaviour... with the field unset the module does not run".
 - Verifier sidecar.py ~616-629 `resolution_check_not_in_journal` is gated `if profile_on:` (profile_on = bool(ops), line ~436); message "under the profile a resolution check carries the id of the journal check". Same in ODES validator tests/data/operation-identity/validate.py 450,518-525 (`profile_on = require_profile or bool(doc["operations"])`).
 - Verifier docs/tiers.md:494-497 (explicit non-claim): "The ids of resolution checks and of journal checks are separate producer ids (the contract says so), and a completed journal check binds to a resolution check by stage, inputs and reasons, not by id; a record whose only change is one resolution check id is still consistent by content, and the verifier does not invent a link between the two id sets." Also tiers.md:147 / rules_journal.py check_bindings: count-based (len(checks) > len(completed)).
 - Not found: any CP/Registry/Verifier text making linkage mandatory without identity. Freshness: CP links ids under freshness too (check_ref gate) but I found no Verifier rule enforcing it without operations ledger (inference from sidecar gating; freshness-only not run).
B. Plain [journal] = RuntimeAuthorityProfile with no opt-ins, with allow_synthetic_resolver=True (tests/test_runtime_authority.py setup_flow 24-51). That flag requires allow_test_time (bounded.py 1288-1290) and bypasses resolver_not_authenticated (2113): the FIXTURE is a test baseline (synthetic resolver, test clock). But the configuration class "journal with no identity/freshness" is the base, default-path runtime-authority profile (opt-in-profiles.md:3 "pinned default path"), contractually valid/supported and issues claims; docs/contract-conformance-execution-attempt-lifecycle.md:26 lists journal sequential checks conformant. So reachable in principle; just not linkage-bearing.

D. To make linkage assertable on plain journal one would have to change production code (pass check_ref unconditionally) or enable identity/freshness (which is the other param); there is no valid fixture-only way: ids differ by design (my probe: journal ids e5547df7/5832b748 vs resolution ids a09673ae/bc691c12). Asserting detection would require the Verifier to invent a link tiers.md:494-497 disclaims. Forcing it = invalid/artificial. The stage-lie half needs no change; it could be split out.

Probe (reproduced; scratchpad probe_q6a.py, PYTHONPATH=src:.:verifier/src): plain journal clean record overall=abstain; zeroed claim resolution check_id overall=abstain, refutations=set(); stage-lie overall=reject. Reviewer's claim confirmed. But 'abstain' here is NOT a verdict about linkage: it comes from 14 could_not_check results (v2.identity.*, v4.ledger.* : manifest/ledger inputs absent) and equals the clean record's verdict; engine.py 91-98 (reject if any refuted; abstain if any not confirmed). Specified outcome for no linkage: no check examines it (silent), per tiers.md:494-497 -> not a refutation.

Strongest counter-argument: ResolutionCheck.check_id and journal check_id share the field name and the CP's own docstring/test intent (the test header "correctly bound claim-stage journal check"; test:84-88 asserts same ids "as on the decision/effect paths") suggest an integrity expectation; a zeroed id on plain journal is silently accepted, and the skip text is the builder's own, not a contract citation; F3 is a "correctly bound" claim. Residual ambiguity is only whether the program wants the plain-journal route to be linkage-bound (a design choice) -- no governing text requires it.

## 5. Masked-host limitation: precise statement

* Where it exists: Control Plane `docs/effective-configuration-binding.md` at 8616d5f section 10 (added by commit 95fe45f, docs only). It is ABSENT at 739efe7: grep for "masked" and "stricter" returns nothing at 739efe7, and the 739efe7 section 10 still says "The binding checks the executing workflow's HOST-supplied values", which is inaccurate against the effective-value behavior. Readjudication S-DOC check `D2_masked_host_change_limitation_stated`: FAIL at 739efe7, PASS at 8616d5f (S-DOC 6 pass / 3 fail at 739efe7; 9/9 at 8616d5f). D-1 did not evaluate 8616d5f and says its results do not transfer there; the readjudication and record 11 state src is code-equivalent (docstring-only difference in `registry_governed_policy.py`). A record bound to 739efe7 must not say the 739efe7 docs contain the limit.
* Scope of the text (8616d5f): "A change in the host configuration that is completely masked by a stricter effective Registry value may not change the effective-configuration binding and therefore may not cause refusal." It applies "only where the workflow's F4 scalars (`status_max_age_seconds`, `approval_max_age_seconds`) or ObservationPolicy values (`max_age_seconds`, `clock_tolerance_seconds`) are narrowed by a Registry family and a host change leaves every effective value and every declared family's effective-policy digest unchanged". Covered by a developer test only for ObservationPolicy `max_age_seconds` 300 to 299 under Registry 60 (`test_b03b_...`); the F4-scalar case "follows from the same code path but has no dedicated test". The same text states the carve-out: "any change to the host PROFILE (`host_profile_digest` is a member, so a host profile edit is refused even if the final profile is identical)" is still refused.
* Consequence for these members: the limit concerns the `f4_scalars` and `observation_policy` members (effective values), not `host_profile_digest` or `effective_profile_digest`. D-1 Q3-H1 exercises the F5 class-age route, where the edited host field is a profile field (class age on the action) overwritten by `compose_profile` (:117). That is the carve-out case (masked profile edit is refused), not a counterexample to the limit, and D-1 provides no evidence about the limit's own F4-scalar / ObservationPolicy cases (no masked-versus-unmasked control for them).
* Record 12 item 2 phrases the limit more broadly ("a host change fully masked by a stricter Registry value is not refused"). That wording overstates relative to the CP text for profile edits; a final record should quote the CP text, not the record 12 paraphrase.
* Not exercised by D-1: the freshness-extension composition clamp (compose_profile :123-126), another masked host-profile route, which `host_profile_digest` should also catch (unverified).

## 7. Strongest counter-argument, and what would flip the labels

Counter-argument (for OPEN — CONTRACT REQUIREMENT UNMET): 03 expectation 1 says each member perturbed makes execute AND pin-export refuse, and 02 rule 2 says execute and pin-export claim "recompute the live member and compare". The only live-side recomputation actually exercised for these two members is on execute (H1, E1, E2). For pin-export and claim issuance, the live-derivation-to-refusal composition is inferred from a shared `_resolve`, which is exactly the "mechanism-level" inference the Architect said does not authorize declaring an unverified behavioral obligation satisfied. Record 12 (class A, "required for the current F3-A acceptance boundary") says the item "needs" independent fixtures and that an unverified outcome must not be converted to PASS. For effective_profile_digest the only live-side evidence is guard-first and joint, so "the member alone causes refusal" is not shown end to end anywhere; a regression dropping it from the live derivation would pass every executed test and (by source reading) change no live-side outcome.
Response: (i) 02/03/06 text asks for independent perturbation, not live-side per-path isolation, and A19/G1/G2/Q5 do perturb each member alone on every contract path; (ii) the pin-export and claim wrappers cannot distinguish which side moved, so the path-specific behavior (the refusal response) is verified and the member-specific behavior (live derivation) is verified on execute; (iii) for effective_profile_digest the dropped-member regression is behaviorally neutral on live routes because `catalogue_digest` and `approval_commitment` in the base binding carry the same information, so no authorization or refusal obligation is weakened; (iv) record 12 and #240 are builder-lineage documents that leave the question to the Architect, who has now stated the interpretation.
If the Architect rejects (i)-(iv), the unmet requirements and exact missing evidence are: host_profile_digest: one F5 class-age masked-host live-side case each on pin-export (state not active, payload None, base diff empty, ECB diff exactly the member leaf) and claim issuance (PermissionError, no claim), with an unmasked-edit control; plus, if breadth is required, the same on policy-composition and class-unreadable. effective_profile_digest: an isolating construction (a graft or reseal whose donor differs in effective_profile_digest only, i.e. persisted-side, equivalent to A19) is already present; a live-side isolated case cannot exist while the member equals `catalogue_digest`, so the requirement would be unsatisfiable by construction and would instead need an Architect ruling (BLOCKED — CONTRACT AMBIGUITY; smallest clarification: "Is a live-side end-to-end case isolating effective_profile_digest from catalogue_digest required, given 02 s4 defines the two as equal?").

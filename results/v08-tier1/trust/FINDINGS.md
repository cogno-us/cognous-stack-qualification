## Findings and characterized limitations
- **F1 (LOW, robustness, owner: Runtime `engine/registry_selection_authority.py`)**: `_verify` catches only `sqlite3.Error` around `_read_log`. A non-canonical or unparseable `selection_log_v1.entry_json` raises `ReplayError("entry_not_canonical"/"entry_unparseable")` out of `_verify`, so `verify_selection_store()` raises instead of returning `unknown`, and the effect guard fails closed WITHOUT a typed `store_unknown`/HOLD refusal (the executor reports a generic `dispatch_error`/`unknown` and no `selection_refusal` evidence). No effect was committed and the claim stayed `issued` in every probe, so this is not a breach. Reproduction: C04 probes `noncanonical_entry_text`, `unparseable_entry_text` (drop triggers, `UPDATE selection_log_v1 SET entry_json=...`, execute).
- **F2 (informational, owner: Runtime/Control Plane)**: with `agent_control_plane.canonical_policy_binding` unimportable the effect is not executed (0 effects, claim issued) but surfaces as `unknown` / `dispatch_error` (ImportError), not as the typed `verifier_unavailable` the guard source intends. Fail-closed, untyped.
- **TR-7(a) A09 (confirmed, characterized)**: the amount ceiling and the target prefixes are owned by the caller's executor policy and are not Registry payload members (payload has only the five sets). A 5,000,000 amount and an out-of-prefix target are denied by a narrow caller policy and EXECUTE under a wider caller policy bound to the same Registry record and claim.
- **TR-7(b) D08 (confirmed, characterized)**: the lock-time path does not re-verify `claim_commitment`. A claim provisioned with a stale `activation_ref` (control: refused `policy_identity_mismatch`) and then edited in `claim_json` to the current activation_ref WITHOUT recomputing the commitment EXECUTED (1 effect). Editing the `source` member was refused by claim-model validation (`ValidationError`, denied, 0 effects). The claim row is therefore trusted by virtue of the database, not self-authenticating; an attacker with database write access can also rewrite far more, so this is a custody limit.
- **TR-7(c) D01**: reproduced in C10 (consistent DB + anchor rollback undetectable, effect commits).
- **TR-7(d) I01**: all 10 Runtime wrapper workflows still call `cognous-stack-qualification` reusable workflows pinned to the single SHA `1c1755ff4ea719cfa12f72bcd8c81dd51cff7fb2`, which is not the V07 pin (`90e0e56e`) nor this checkout's HEAD. The commit is not present in this repository's object database, so ancestry (older than the qualified revision) could not be proven locally; the finding that the pin differs from the qualified revision is TRUE. Not a pass.
- **Informational**: PyNaCl blocked in a separate process does not affect an effect-time execution (the guard needs no signature verification; the claim executed); pydantic 2.11.9 provisions a successor claim without error (the "successor profile unsupported on 2.11.9" assumption does not hold at provisioning; effect-time under 2.11.9 not exercised); the legacy Control Plane refuses the successor claim at provisioning with `execution claim commitment is invalid` (its model drops `policy_binding`), a fail-closed refusal with a different reason than the source comment; pretty-printed (non-canonical whitespace) selection envelope text is accepted because the signature covers the canonical statement.
- **Harness note for the lead**: `conftest.pytest_collection_modifyitems` counts all collected items before `-k` deselection, so `-k` cannot be used after the first run (it refused with 5+13>15 and ran nothing, ledger unaffected). I used explicit node ids. No budget was consumed by those refused invocations.

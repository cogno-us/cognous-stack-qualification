# Worker A (authority and policy) case inventory, committed BEFORE any test execution

Assessor: Worker A, fresh AI session, no prior implementation involvement, same organization (independent test design within the organization, NOT independent external qualification).
Designed from: Registry r08-v2 contract (+ amendments 1-3, ADR EXT-S4-0), Control Plane `local_authority_effect.py` / `canonical_policy_binding.py` / `policy_binding.py`, Runtime `local_authority_effect.py`, `registry_selection_authority.py` (`check_effect`, `_check_policy_containment`, `_check_unbound`), `atomic_local_control_plane_executor.py`, `registry_f1a_narrowing.py`. No test file was opened before this commit.

Source facts that shaped the design (read from source, to be confirmed by execution):
* `AtomicLocalControlPlaneExecutor.provision_claim` does NOT forward `policy_binding` / `expected_consumer_id` / `expected_operation`. A workflow-issued successor claim therefore must be produced by calling `agent_control_plane.local_authority_effect.provision_local_execution_claim(workflow, proposal, decision, provision=destination.provision_claim, policy_binding=..., expected_consumer_id=..., expected_operation=..., now=...)` directly. That is the real materialization path and is what AU-1 uses (executor.execute then carries the claim).
* Effect-time order in `check_effect`: store known -> binding well-formed -> row exists/lineage -> withdrawn/revoked -> activation_ref (stale vs mismatch) -> epoch -> selection_digest -> record triple -> high-water/floor -> revoked pair/key -> window -> ratchet -> trust snapshot -> executor digest == binding digest -> containment (`policy_not_subset:<set>`).
* Unbound (legacy) claims: `_check_unbound` refuses `selection_missing` for ratcheted / revoked / active-in-window scopes, else records `fallback_caller_policy`.

Common oracle facts recorded for every refusal case: executor result status `denied`; `result.control_plane_evidence["selection_refusal"]` = {code, refusal_class, cause} equal to the expected typed triple (the intended reason, not an incidental one); row counts in `effects`, `attempts`, `authority_effect_receipts_v1` are 0 for the claim under test; claim state still `issued`; budget `used_effects` unchanged. A positive case requires exactly 1 effect, 1 attempt, 1 receipt, claim `consumed`, budget used 1, and receipt `selection_guard.result == "binding_verified"` with the activation_ref/epoch of the live activation. Nothing uses distinct OS processes (this area is single-process by design; concurrency/crash belong to Worker B).

Test items (pytest executions) group sub-probes that each use a fresh database; every sub-probe is a separate inventory case below (15 cases, 10 pytest items planned, 5 executions held in reserve for reruns).

# Verifier mutation harness (design stage S5, family T)

Opt-in, report-only measurement of the independent verifier (`cogno-us/cognous-open-control-stack-verifier`, command `cognous-verify`) against damaged traces. Design: `docs/engineering/INDEPENDENT-VERIFIER-DESIGN.md` in `cogno-us/open-decision-evidence-standard` (sections 4.1 to 4.5). Report shape: the ODES `verification-report` draft (`mutation_report`), vendored unmodified in `contract/verification-report` (see its `CONTRACT.json`).

It selects no component, changes no scenario verdict, profile or pin, runs no qualification controller and no `tools/v1_validation.py` mode, and is not a required check. Standard library only. Family S (control-removal) counts are context only and are never produced here; `--family-s FILE` can carry them, with their own denominators.

## Run

```
# harness proof with stubs (default CI does this)
python -m unittest tests.test_verifier_mutation_harness

# measurement (workflow verifier-mutation-report.yml does the same; dispatch only)
PYTHONPATH=suites/verifier-mutation python -m verifier_mutation report \
  --odes <ODES checkout> --out mutation-report.json --jobs 4 \
  --per-operator per-operator.json \
  --verifier-cmd 'cognous-verify {run_record} [--proposal {proposal_export}] [--manifest {manifest}] [--ledger {destination_ledger}] [--witness {witness}] [--holder-inventory {holder_inventory}] --json'
```

Catalogue version 3 runs a second, witnessed population by default (`--witnessed-corpus`, `--no-witnessed` to skip): the witnessed traces and their family H, B and F mutants, with the witness and inventory passed through the `[--witness {witness}]` and `[--holder-inventory {holder_inventory}]` groups. An H8 empty-witness mutant passes an empty file; the absent-file variant (`H8.witness-file-absent`, catalogue version 3.1) passes a path where no file exists and is an input-error control: the expected outcome is exit 2 with no report (ODES decision 30-A), not abstain. `--per-operator` writes a breakdown per operator (verdicts, codes, the mutants not handled as expected); its counts sum to the report's rows and add no figure.

A `[...]` group in the command is passed only when the trace has that file; seed documents carry a run record only. `--strict` exits 3 when a harness flag is raised; by default a flag is an advisory in the report and the run exits 0.

Regenerate the clean corpus (opt-in; needs the control plane virtualenv with `cryptography`): `python -m verifier_mutation capture --control-plane <checkout>`; the witnessed corpus: `python -m verifier_mutation capture-witnessed --control-plane <checkout>` (the checkout at the clean corpus's revision, 128eaa5; `report` refuses a witnessed corpus from another revision). Capture is not byte-repeatable (the stack mints identifiers), so the corpus digest, not the script, identifies the corpus.

## Counting rules

- Corpora are never pooled: `t-seed-odes` (ODES fixtures, regression only: `k` of `n` seeds refused with the intended code, no detection, no metric impact), `t-generated` (operator mutants of the clean traces: detection with any code and with the intended code, false acceptance, abstain, error on separate lines, metric impact conditioned on false acceptance), and per clean corpus the clean-trace false rejection. Per-scenario tables repeat the generated rows over each scenario's own slots (one trace per scenario here).
- A slot is one (trace, operator variant, draw). `n_na`: precondition not met. `n_noop`: files identical to the clean trace (a structural operator also when canonically equal). Identical mutants of one trace and operator are dropped and counted in the harness extension. `n_eff = n_gen - n_noop - n_na`. Verdicts sum to `n_eff`.
- Divergence from the design text: noop is decided on files, not on a lenient re-parse, because a duplicate member or `NaN` reads as the clean document under Python's parser yet is the damage being measured.
- Clean false rejection per category counts the clean traces on which that category's operators produced an effective mutant; benign (B) counts benign mutants. For the ODES valid fixtures the row covers the valid fixtures of the contracts that category's seeds come from, so rows repeat the same fixtures.
- Metric impact measures are derived by this harness from the files (the verifier does not expose them); unavailable (counted aside) for an accepted mutant Python cannot parse.
- Intended codes are frozen with the operator set. A different but correct verifier code counts in `any_code` only. In catalogue version 1 they were frozen before the verifier ran, with working names where no ODES contract or verifier code existed. In catalogue version 2 they were rewritten after run 1 was read (see the change log): **intended codes frozen post-hoc after run 1 (703cdde1)**. `any_code` detection is the primary figure; localized (intended-code) figures are secondary, are reported separately, and are never held-out.
- J3 is realized as completed-to-interrupted or completed-event-dropped: no real clean trace holds an interrupted check to rewrite.
- Expected-accept categories (B, F, R6) are reported with the same columns; an accept there is the expected outcome, not a failure. In catalogue version 2, B also holds the float-spelling, renamed-check-id and similar value-equal variants (post-hoc), and R6 is only a ledger row that nothing in the record corroborates.
- Held-out: for run 1 the operator set and seed were fixed in this repository before the verifier was run; the clean bases are the same scenario family the verifier's own tests use, so only the mutants were held out. Run 2 is NOT held-out: the catalogue (version 2), the intended codes and one added clean trace were written after run 1 and the verifier follow-up (V3a) were read. Its figures are a re-measurement, not a fresh blind one.
- Witnessed population (catalogue version 3, ODES decision 28): family H is measured only on witnessed traces. Its generated corpus (`t-generated-witnessed`) carries only H1 to H8 and the B and F controls measured on the same traces, its clean corpus (`clean-generated-witnessed`) is separate from the unwitnessed one, and its seeds (`t-seed-odes-witness`, `clean-odes-witness-valid`) are separate from the unwitnessed seeds; nothing is pooled across the two populations (the vendored validator refuses a mixed corpus, `witnessed_corpus_mixed`, and a witnessed corpus without its clean corpus, `witnessed_clean_corpus_missing`). Expected verdicts: H1 to H6 reject, H7 and H8 abstain, B and F accept. For H7 and H8 an accept is a false acceptance and a reject a false rejection; both show in `verdicts`, and `detection.any_code` on those rows is not detection. Tier V3 ran, so the report lists the witnessed clean corpus's witness files and inventories under the roles `witness` and `holder_inventory` (the contract ties V3 to such an input) and carries the non-claim `witness_is_not_publication`.
- Witness seeds: a witness fixture without a `record` is run with the record of `staged-two-records-chained`, a holder-inventory fixture with the record and witness of `run-with-holder-inventory-journal-mode` (`witness-seed-map.json` `carrier`). A seed is credited when the verifier refuses it with the fixture's ODES code or the verifier's name for the category's rule (the shape codes differ by name; ODES drafts, Divergences). `empty-witness-file` is an H8 control, not a regression seed: its observed verdict is in the harness extension (`witnessed.seed_controls`). Seeds run without a proposal, so a valid seed's best outcome is `abstain` (identity checks could not be made), as for the unwitnessed seeds.
- Flags (`no_detection_anywhere`, `accepts_every_mutant`, `abstains_on_every_mutant`, `rejects_every_clean_trace`, `rejects_every_valid_seed`, `errors_present`) say the verifier is not measuring anything. They gate nothing.

Nothing here claims a decision is correct or that the verifier is correct; figures are counts over the stated corpora and say nothing outside them.

## Witness damage is not in this catalogue (decision recorded 2026-10-18, stream Q2)

**Superseded the same day** by ODES decision 28 (family H, H1 to H8, admitted to the design and the report contract) and catalogue version 3 below. The text is kept as written for the record; its conclusion (a new category and an ODES report-contract change first, then a frozen witnessed corpus with provenance, then a catalogue version 3 labelled post-hoc) is what was then done.

The verifier gained tier V3 (`--witness`, `--holder-inventory`) and its codes (`witness_chain_invalid`, `witness_ledger_head_mismatch`, `witness_ledger_shrunk`, `witness_record_shape`, `witness_run_mismatch`, `witness_version_unsupported`, `rows_not_covered_by_witness`, `holder_inventory_missing`, `holder_inventory_shape`). Those names are in `verifier-code-names.json` (so an operator may name them), but **no witness operator was added and the catalogue stays at version 2 with 81 operators** (`operators.json` is unchanged; run 3 uses the same operator-set digest as run 2).

Why: the design's 36 categories (`INDEPENDENT-VERIFIER-DESIGN.md` section 4.3) are closed and each names damage to the record, the proposal or the destination ledger. Witness damage does not fit one of them without stretching it:

- A broken witness chain, a witness for another run, an unsupported witness version and a malformed witness record damage a fourth artifact (the witness file), which no category covers. The nearest, X1 ("transplanted from another run"), names a decision, a proposal or a ledger row, not a witness.
- Dropping, emptying, rewriting or swapping the first rows of a destination ledger while a witness covers them resembles R5/R6. But R6 is defined as the case that is undetectable without sequence and chain, with expected verdict `accept`; with a witness that case becomes detectable, which is a different expectation on a different tier (V3) and a different input. Folding it into R6 would redefine R6, and putting it in R5 would change what R5 measures.

Adding a category would change the design and the report contract's closed category list, which this stream may not do. So witness damage is tracked where it already is: in the verifier's own tests (`tests/test_witness.py`, `tests/witness_mutations.py`, and its differential against the control plane's `verify_against_witness`; figures are the verifier's, not measured here; see the verifier repository). Run 3 therefore runs tiers V1, V2 and V4 only (the report says `tiers_run: [V1, V2, V4]`), exactly as runs 1 and 2 did: no run here passes `--witness`. If the owner wants witness damage measured under this harness, the design needs a new category (and an ODES report-contract change) first, then a frozen witnessed-corpus snapshot with provenance (the verifier's `tools/capture_witnessed_runs.py` is the capture path) and a catalogue version 3 written after seeing the verifier's V3 behaviour, so its intended codes would not be held out.

## Change log

### Harness fix (stream Q5): lone-surrogate seeds are loaded and written as wire bytes; no catalogue change

The ODES `unpaired-surrogate-text` fixtures hold a text member with an unpaired surrogate code point. Loading one crashed the seed loader (`UnicodeEncodeError` in `dump_file_bytes`: a lone surrogate cannot be UTF-8 encoded). The writer now encodes such text with `jsonio.wire_text_bytes`, which writes each lone surrogate as its six-character JSON escape, the form the fixture file holds and the verifier's wire layer refuses (`wire_lone_surrogate`); text without one is encoded exactly as before, so no existing digest changes. The four seeds that reach the harness (`control-plane-journal`, `execution-attempt-lifecycle`, `witness-digest`, `holder-inventory`) are now classified: the first two as W4 with intended codes `schema_violation` or `wire_lone_surrogate` (`intended_codes_by_fixture` in `seed-map.json`), the other two as H3 and H6 in `witness-seed-map.json`. Operator ids, functions, intended codes and mutants are unchanged (catalogue 3.2); `operators.json` changed only in the `implementation_sha256` of `jsonio.py` and `corpus.py`. No retained run was made for this change.

**Misses and open items (findings about the verifier and the design; no operator was weakened):**

1. `H4.ledger-removed`, 12 of 31 abstained instead of rejected. When the removed ledger is `decisions` or `attempts` (the members the verifier uses to recognise the document kind), the record is classed `unsupported_document` and every check, V3 included, becomes `could_not_check`: the witness says a covered ledger had rows, the record no longer has the ledger, and the verifier abstains (exit 3) instead of reporting `witness_ledger_shrunk`, which the control plane's own `verify_against_witness` reports for a vanished ledger ("a ledger that disappeared counts as emptied") and the witness-digest draft's rule says. Not an acceptance, but not detection either. Verifier owner: when a witness is supplied and the record is a JSON object carrying the witnessed `run_id`, run the V3 ledger-head checks (a missing ledger counts as empty), or refuse the record as a malformed record store document rather than abstaining.
2. `H4.destination-row-dropped-uncorroborated`, 1 of 1 accepted. The design (section 4.3, R6 and H4 rows) and the report contract say "with a witness the same drop is H4". The `witness-digest/0.1` profile covers only the run record's list-valued members; the destination ledger snapshot (`destination.json`, an object of rows) is a different file that no witness covers, so the drop is as undetectable with a witness as without (R6). This is a design/profile gap, not something the verifier can fix alone: ODES owner: correct the R6/H4 sentence (the witness does not cover the destination ledger) or extend the profile to witness the destination snapshot (a new profile version); one trace, an anecdote, not a rate.
3. `H8.witness-file-absent`, 17 of 17 error: `--witness` naming a path where no file exists makes the verifier exit 2 with no report (input error), so the harness counts `error`, never abstain or detection. The contract expects H8 `abstain` and its default 29 left this case open. Verifier owner and ODES owner: decide whether a missing witness file is an input error (then the H8 definition should say "witness holding no digest" only) or an abstention (`could_not_check`, `input_absent`). Raises the advisory flag `witnessed_errors_present` (17/2075).
